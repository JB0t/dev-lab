# Multi-Application Canary Monitoring

This solution provides comprehensive monitoring for canary deployments across multiple applications in a Kubernetes cluster with Linkerd service mesh and Flagger progressive delivery.

## Dashboard Solutions

### 1. Multi-Application Dashboard

**File**: `infrastructure/monitoring/multi-app-canary-dashboard.json`

**Features**:
- **Dynamic Application Discovery**: Uses Prometheus queries to automatically discover canary deployments
- **Namespace and Application Filtering**: Template variables allow filtering by namespace and workload
- **Unified View**: Monitor all applications from a single dashboard
- **Comparative Analysis**: Side-by-side metrics across applications

**Template Variables**:
- `$namespace`: Filters by namespace (supports multi-select and "All")
- `$workload`: Filters by application name (supports multi-select and "All")

### 2. Application-Specific Dashboards

**Generated by**: `scripts/generate-canary-dashboards.sh`

**Features**:
- **Focused Monitoring**: Dedicated dashboard per application
- **Deep Dive Metrics**: Application-specific SLA thresholds and KPIs
- **Custom Branding**: Application name and namespace in title and panels

**Auto-generated for**:
- `mesh-test/mesh-test-app`
- `order-system/order-service`
- Any future canary deployments

## Key Metrics Monitored

### Traffic Management
- **Canary Weight**: Percentage of traffic routed to canary version
- **Traffic Distribution**: Primary vs Canary request rates
- **Request Rate**: Total requests per second per application

### Reliability Metrics
- **Success Rate**: Percentage of successful requests (non-5xx responses)
- **Response Latency**: P50, P95, P99 latency percentiles
- **HTTP Status Codes**: Distribution of response codes

### Security Metrics
- **mTLS Coverage**: Percentage of traffic encrypted with mutual TLS
- **TLS Connection Breakdown**: Secured vs unsecured traffic

### Operational Metrics
- **Canary Phase**: Current deployment phase (Progressing/Succeeded/Failed)
- **Health Status**: Application health check status
- **Load Balancing**: Traffic distribution across pods

## Application Configurations

### mesh-test-app
- **Namespace**: `mesh-test`
- **Replicas**: 5 pods
- **Canary Strategy**: 10% increments, max 50% traffic
- **SLA**: 95% success rate, 500ms P99 latency
- **Health Checks**: Liveness and readiness probes on port 3000

### order-service
- **Namespace**: `order-system`
- **Replicas**: 3 pods
- **Canary Strategy**: 5% increments, max 30% traffic

## Scripts and Automation

### Dashboard Generation
```bash
# Generate dashboards for all discovered canary deployments
./scripts/generate-canary-dashboards.sh

# Generate dashboards for specific namespace
./scripts/generate-canary-dashboards.sh "order.*"

# Generate and upload to Grafana (requires token)
GRAFANA_TOKEN=your_token ./scripts/generate-canary-dashboards.sh
```

### Canary Testing
```bash
# Test mesh-test-app canary deployment
./scripts/test-canary-deployment.sh mesh-test-app v8

# Test order-service canary deployment  
./scripts/test-canary-deployment.sh order-service v2
```

## Monitoring Workflow

### 1. Discovery Phase
```bash
# Check available canary deployments
kubectl get canaries -A

# Generate fresh dashboards
./scripts/generate-canary-dashboards.sh
```

### 2. Deployment Phase
```bash
# Trigger canary deployment
./scripts/test-canary-deployment.sh order-service v2

# Monitor progress
kubectl get canary order-service -n order-system -w
```

### 3. Monitoring Phase
- **Multi-App Dashboard**: Overview of all applications
- **Individual Dashboards**: Detailed metrics per application
- **Alerting**: Configure alerts based on SLA thresholds

## Scaling to New Applications

### Adding a New Application

1. **Create Application Structure**:
```
apps/
  new-service/
    ├── Dockerfile
    ├── k8s/
    │   ├── base.yaml
    │   ├── canary.yaml
    │   ├── metrics.yaml
    │   └── kustomization.yaml
    └── scripts/
        └── build.sh
```

2. **Deploy Application**:
```bash
kubectl apply -k apps/new-service/k8s/
```

3. **Generate Dashboard**:
```bash
./scripts/generate-canary-dashboards.sh
```

4. **Test Canary**:
```bash
./scripts/test-canary-deployment.sh new-service v2
```

### Dashboard Auto-Discovery
The monitoring solution automatically discovers new canary deployments through Prometheus queries:

```promql
# Discover namespaces with canaries
label_values(flagger_canary_weight, exported_namespace)

# Discover applications in namespace
label_values(flagger_canary_weight{exported_namespace=~"$namespace"}, workload)
```

## Best Practices

### 1. Naming Conventions
- **Namespace**: `<service>-system` or `<service>-test`
- **Application**: Kebab-case names (e.g., `order-service`, `user-api`)
- **Canary**: Same name as deployment

### 2. SLA Configuration
- **Success Rate**: >= 95% for user-facing services
- **Latency**: P99 < 500ms for interactive services
- **Traffic Increment**: 5-10% steps for gradual rollout

### 3. Monitoring Strategy
- **Multi-App Dashboard**: Operations team overview
- **Individual Dashboards**: Development team deep-dive
- **Alerting**: Slack/PagerDuty for canary failures

### 4. Testing Strategy
- **Load Testing**: Use Flagger's webhook tests
- **Health Checks**: Comprehensive readiness/liveness probes
- **Rollback**: Automatic on SLA violations

## Troubleshooting

### Common Issues

1. **Canary Stuck in Progressing**:
   - Check metric template configuration
   - Verify Prometheus connectivity
   - Review webhook test results

2. **No Metrics in Dashboard**:
   - Confirm Linkerd proxy injection
   - Check Prometheus scraping configuration
   - Validate service discovery

3. **Dashboard Variables Empty**:
   - Verify Prometheus data source
   - Check metric query syntax
   - Confirm time range settings

### Debug Commands
```bash
# Check canary status
kubectl describe canary <name> -n <namespace>

# View Flagger logs
kubectl logs -n linkerd deployment/flagger

# Check Linkerd metrics
linkerd viz stat deploy -n <namespace>

# Test Prometheus queries
kubectl port-forward -n monitoring svc/prometheus-kube-prometheus-prometheus 9090:9090
```
